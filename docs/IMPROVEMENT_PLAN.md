# 旅游助手下一阶段改进方案

编写日期：2026-10-26。状态：设计方案，尚未实施。

本方案基于当前代码和上一轮开源调研。现有原型已经具备攻略、主规划、酒店三个角色的独立上下文，以及真实 POI、住宿决策、自然语言调整、独立校验和版本确认。本阶段优先提升推荐与路线质量，再补交互和执行恢复，不以增加 Agent 数量作为目标。

## 1. 目标、范围与执行顺序

目标体验：用户输入“成都三天，带父母，喜欢历史，少走路”，系统据此查找有依据的地点，按区域组织行程，展示推荐理由和待核实项；用户指定第三天去某家店后，系统保留硬要求、协调普通推荐，并提供经过校验的调整选项。

| 顺序 | 里程碑 | 交付物 | 工作量估计 |
| --- | --- | --- | --- |
| M0 | 建立质量基线 | 固定任务、Provider 夹具、指标与基线报告 | 1～2 人日 |
| M1 | 需求与候选属性 | 旅行画像、字段证据、兼容旧版本的契约 | 2～3 人日 |
| M2 | 按需检索 | 查询计划、候选合并、精确地点消歧、快照 | 2～3 人日 |
| M3 | 排序与空间规划 | 多目标筛选、按天分组、有限路线验证 | 3～5 人日 |
| M4 | 可操作的候选与冲突交互 | 地点引用、备选池、选择卡、变更对比 | 2～3 人日 |
| M5 | 研究复用与执行恢复 | 输入依赖、有效期、任务恢复、按需调度 | 3～5 人日 |
| M6 | 出行使用模式（后续） | 已完成/跳过、导航、打印导出 | 1～3 人日 |

估计按一人熟悉当前代码计算，不包含外部服务开通和不可控数据整理。先完成 M0～M3 并比较结果，再决定 M4～M6 的投入。每个里程碑独立验收，不一次性重写全部流程。

沿用 Python、FastAPI、Pydantic、LangGraph、SQLAlchemy、React 与高德。当前仍支持中国大陆单城 1～3 天、个人本地使用；酒店只提供位置与通勤参考。暂不增加房价、支付、自动预订、跨城交通库存或多用户发布。

## 2. 现状与需要修正的接入点

| 当前实现 | 实际影响 | 改造要求 |
| --- | --- | --- |
| `main.py` 的 `/api/places/discover` 只接收 `CityQuery`；`tools.py:discover` 固定查景点、博物馆、咖啡、步行街 | 旅行偏好无法影响初始召回 | 新接口接收需求草稿，先形成旅行画像和查询计划 |
| `App.tsx:discoverPlaces` 只发送城市；重新查询会清空必去选择 | 后填偏好不能重查，刷新候选可能丢失用户决定 | 调整表单顺序，保留已有明确选择；显示资料是否仍匹配当前需求 |
| `Place` 室内字段是布尔值，时长是单值；真实 POI 依类别推测 | 未知属性容易被当成已知事实，无法区分建议与证明 | 增加可表达未知的属性和字段级来源；保留旧字段兼容 |
| `llm.py` 从已有目录选择；`planner.py` 多日时可能补回全部目录 | 只修改召回或排序，排程仍可能重新塞入低质量候选 | 显式传递允许集合、备选集合和每天分组；新增候选须重新准入 |
| `replanning.py` 有独立的有限景点补查 | 初始生成与后续调整可能采用不同过滤规则 | 共用检索、消歧、属性和排序服务；保留调整范围与补查预算 |
| 攻略有来源链接与结构化摘要，但未逐字段绑定事实 | 有引用不等于每个营业、适合人群等判断有证据 | 地点、属性、时间信息分别绑定证据和未知状态 |
| 任务结果已落库，重启将运行中任务标为中断 | 能诊断中断，不能自动继续有效工作 | M5 引入可恢复的阶段产物与执行领取机制 |

保留已有的必去地点、指定日期、锁定预约、酒店、抵离条件、预览确认、幂等与版本 CAS。禁止通过删除用户要求、放宽限制或静默切换演示模式制造成功。

## 3. M0：先建立可比较的质量基线

### 任务

1. 在 `evals/datasets/` 新建 `travel-quality-v1.json`，先完成 12 条代表任务，M3 验收前扩展至不少于 30 条。
2. 覆盖历史文化、夜景拍照、亲子、少步行、雨天、晚到早走、指定日期、同名分店、固定预约、远距离必去、检索空结果和限流。
3. 每条任务记录需求、明确约束、人工可接受候选集合、禁止候选、预期澄清点、Provider 数据版本。不要规定唯一正确路线。
4. 使用自建或可再分发的脱敏 Provider 夹具，覆盖坐标、来源、属性缺失与路线；固定算法随机种子（如使用）、预算、模型和 Prompt 版本。程序回归可使用冻结的模型响应；真实模型比较每条任务至少重复 3 次，报告均值、范围和失败，不承诺模型输出完全确定。真实在线样例单独记录。
5. 扩展 `scripts/evaluate.py` 或增加 `scripts/evaluate_quality.py`。保留原 10 条确定性冒烟任务，不将其通过率解释为旅行推荐成功率。

### 指标

| 指标 | 计算方式 |
| --- | --- |
| 硬要求满足率 | 检查必去、日期、固定时间、酒店与抵离；同时报告逐项通过率和整条任务全部通过率 |
| 候选相关性 | 使用人工标注的候选相关等级，计算 Recall@K、nDCG@K；没做完整标注的任务单独列出 |
| 主题与类型多样性 | 统计非用户指定的重复类型、连锁同类堆积和每日主题覆盖；结合人工判断，避免惩罚明确的博物馆主题游 |
| 行程质量 | 交通总时长、明显折返、每日活动和休息负担；未知步行距离与景区内部步行单独标记 |
| 证据质量 | 已标为核实的字段是否有正确来源，抽样判断来源是否真正支持该说法 |
| 修改稳定性 | 非目标日期与用户保护项的变化、普通推荐删除数、跨日移动数 |
| 效率 | 模型调用和 Token、实际上游请求数、缓存命中、耗时；区分工具调用次数与真实 HTTP 次数 |

先记录现状，再使用相同输入与资料比较：A 当前方案，B 按需检索和排序，C B 加空间分组。保留效果差的样例，汇总回归项；评测集留出一部分，不把全部任务用于调权重。

### 验收

- 提供可重复运行的离线命令和逐任务结果，能定位失败属于检索、选择、排程还是证据。
- 硬条件违规的方案一律不能确认；未知属性不能被统计为已满足。
- 不预先宣称提升百分比；M3 报告真实收益、退步样例与额外成本。

## 4. M1：旅行需求与候选属性契约

### 4.1 旅行画像 `TravelProfile`

在现有 `Requirements` 上增加有默认值的结构化画像，保留 `interests`、`pace`、`note`。前端提供少量常用选项和自然语言备注，显示可编辑的理解结果。

| 字段 | 内容与约束 |
| --- | --- |
| companions | 独行、朋友、亲子、与父母等用户明确说明；不推断年龄或身体状况 |
| themes | 历史、建筑、夜景、摄影、自然、美食等细分主题；每项记录用户表达与来源 |
| walking_preference | 少步行等软偏好；用户明确给出的每日距离/单段时长上限单独记为硬条件 |
| pace / rest_preference | 每日密度、休息频率；用户可编辑，不将“带父母”自动转换成固定限制 |
| exclusions | 明确不去的类型、地点或活动，区分硬排除与不太喜欢 |
| clauses | 需求条目、硬/软性质、原文片段、对应结构字段及待澄清状态 |

简单选项由程序归一化；自由文本最多一次有界模型解析。只能抽取用户表达，不新增必去地点、预算或行动能力判断。模型不可用时保留结构化选项和原文；未理解的明确硬要求须澄清，不能悄悄忽略。

### 4.2 候选增强 `PlaceTraits` 与 `AttributeEvidence`

稳定地点身份继续用 Provider POI ID；旅行画像不能改变地点身份。建议在 `Place` 增加有默认值的 `traits`，查询匹配和排序分数放在候选结果中，不伪装成地点永久属性。

| 属性 | 表示方式 |
| --- | --- |
| activity_types / themes | 多标签，保留 Provider 原始分类和归一化映射；交通站、售票处等不得误作普通景点 |
| indoor_outdoor | `indoor / outdoor / mixed / unknown`；支持字段来源与估算状态 |
| duration_range | 建议最短/最长停留与本次选用时长；来源可以是用户输入、资料或明确的启发式估计 |
| audience_notes | 适合人群的理由和证据；资料缺失时未知，不生成“已验证适老”标签 |
| walking / stairs | 已知步行和台阶信息；没有数据保留未知，不能用地点类型证明无障碍 |
| opening / reservation | 营业、最晚入场、闭馆日、预约分别表达；日期适用范围单独存储 |
| evidence / unknowns | 字段值、来源 ID、证据片段、采集时间、适用日期、`observed / user_confirmed / inferred / unknown` |

未知不等于不适合，也不等于已满足。对用户明确的无障碍硬要求，缺少资料时提示未核实或要求确认；不能仅因分类或模型常识直接判定满足。

旧 `indoor`、`duration_minutes` 暂时保留，统一通过解析函数得到有效属性。旧真实 POI 的布尔室内和固定时长标记为历史估算，不能自动升级为已核实；自建演示夹具继续明确标记。

### 4.3 快照与兼容

- `CatalogRecord` 增加检索元信息：`schema_version`、规范化需求指纹、查询计划、检索时间、策略版本、部分失败状态。
- 地点属性证据随现有 catalog JSON 快照保存；不要只存在进程缓存。历史版本仍读取当时的证据，不跟随全局资料更新。
- 新字段带默认值，读取旧 JSON 先通过统一适配器；同步 Python Schema、TypeScript 类型和演示数据加载。
- 新元信息列通过下一条 Alembic 迁移添加；备份现有 SQLite 并测试旧库升级。未知的历史检索画像明确标为 legacy，不推测补写。
- 一次确认仍原子保存需求、目录与行程；M5 的执行快照不能替代行程版本。

### 验收

- “喜欢历史、少走路”和“夜景拍照”产生不同画像；“带父母”本身不会生成无障碍硬约束。
- 未知室内外、估算时长和营业资料缺失都能被前后端准确表达。
- 旧行程读取、修改、取消、确认和恢复不丢字段、不自动升级证据状态。

## 5. M2：按需求形成查询计划与候选池

### 5.1 API 与表单

新增 `POST /api/places/recommendations`，接受城市、日期/天数、兴趣、画像、备注、已选地点及已有 catalog ID 的需求草稿。使用专门的请求 Schema，避免要求用户先完成酒店、抵离信息才能查候选。

返回 `catalog_id`、需求指纹、画像、查询摘要、候选、已保留选择、未知项和部分失败提示。旧 `/places/discover` 暂时保留，内部转发为默认画像查询，避免破坏原调用方。

前端将兴趣、同行人、步行偏好和备注移到候选查询之前。修改影响召回的字段时标记“候选可能需要更新”，由用户点击重新查询；不随每次输入自动消耗额度。点击生成时重新核对画像与候选匹配，过期时提示刷新或按新要求补查，不能无声沿用旧画像。

刷新候选保留用户已经选中的同城必去地点、预约及其证据；切换城市仍明确清空不兼容地点。请求包含客户端序号/指纹，迟到响应不得覆盖更新后的城市或需求。

### 5.2 查询计划 `DiscoveryPlan`

查询条目包含意图 ID、关键词、允许 POI 类型、城市、可选位置锚点、优先级和触发条件。

示例：

- 历史 + 少步行：优先查历史博物馆、文博展馆、相对集中的历史街区；辅助检索交通可达与休息信息，不声称已核实少步行。
- 夜景 + 摄影：优先查夜景观景、滨水夜游和建筑街区；关注开放时段依据，未知时不擅自保证夜间可入内。
- 精确指定某家店：以名称和行政区查询，保留分店区别；歧义时让用户选择。

先用可测试的主题/类别映射生成查询；模型只补充有界的同义表达和缺口，不放任其无限搜索。攻略可以提供查询线索，但每个新增地点仍需解析为真实 Provider 身份和坐标。

### 5.3 查询、合并与补查

1. 初始最多 6 个不同 POI 查询，每次最多 6 条；结果不足才使用最多 2 个缺口查询。失败也消耗查询预算，完全重复复用缓存。
2. 仅按需做一次城市地理编码；已有有效城市区域信息时复用。全部高德请求继续通过同 Key 串行网关、退避与任务总时限。
3. 优先按相同 Provider ID 去重；没有 ID 的结果不进入真实规划。相似名称只作重复线索，不合并不同分店。
4. 保留最多 40 个新普通候选；用户必去、预约和已有保护地点另行保留，不因相关性、离群或截断而丢弃。
5. 初始与增量查询共用类型、坐标、城市和异常结果检查。行政区边缘或同名城市结果不能仅凭字符串相似直接放行。
6. 按缺口补查，例如缺室内候选或某天指定区域候选；用“缺什么、为何查、查到什么”记录轨迹。
7. 自然语言调整沿用当前每次最多 2 次补查、每次最多 5 条；不得因复用新服务而扩大预算或修改范围。
8. 不给每个 POI 单独发模型请求或读取网页。资料补充优先集中处理少量高排名候选，剩余属性保持未知。

以上是起始预算，和模型超时、路线预算一起受统一 deadline 约束；没有时间时返回明确的部分结果。精确点名没有找到时提示未完成，不能用相似地点替代。

### 验收

- 相同城市、不同画像的主要查询与候选排序有可解释差异；存在对应 Provider 资料的测试任务应召回人工标注的相关候选。
- 必去刷新不丢失，同名分店不自动替代，迟到响应不覆盖当前需求。
- 空结果、接口不可用、预算耗尽有不同状态；全部错误路径不泄露 Key。

## 6. M3：相关性、多样性与空间规划

### 6.1 先保护约束，再选择普通候选

必须保留集合包含必去、预约、指定日期和用户锁定项。明确排除与保护项冲突时先澄清；不能通过打低分丢弃保护项。

对普通候选建立可解释的评分分项：需求匹配、证据完整性、类型冗余和预计绕路成本。每项归一化到可比较尺度，权重放在版本化策略中，用留出的评测任务检查，不把模型生成的数字作为客观质量分。

集合选择采用贪心边际增益：每加入一个地点，重新计算与已选地点的主题覆盖和同类冗余；与当前位置的距离随插入位置变化。不要只对全部地点算一次静态总分。

- 相同主题的博物馆适度去冗余，但明确的文博主题游允许多个博物馆。
- 咖啡休息默认作为辅助活动，普通推荐不连续堆叠；用户明确咖啡探店时可增加。
- 类型多样性是软目标，不能强行把不感兴趣的类别塞进路线。
- 不使用缺失的评分、评论数或热度字段伪造受欢迎程度。
- 输出每个候选的匹配理由、排除/降序理由与分项，便于调试和回归。

### 6.2 按区域与日期组织

1. 将坐标统一到适合距离计算的表示；不能直接把经纬度差当米，不能混算 GCJ-02 与 WGS84。用于导航的坐标保留 Provider 所需格式。
2. 在内存中用直线距离生成空间邻近关系；先采用确定性的距离分组/区域划分，不直接引入完整 TSP 求解器。
3. 每日容量按可用时段、活动时长、休息和交通余量估计；第一天与最后一天考虑抵离窗口。不要简单按地点数量均分。
4. 预约、指定日期、已选酒店和抵离位置是日期锚点；区域分组围绕锚点形成可调整建议，不能覆盖日期约束。
5. 远距离必去保留，并解释交通代价。跨区、过桥等场景的直线距离只用于粗筛，最终需要路线验证。
6. 区域不必严格等于一天；允许同一区域跨日，也允许一个日期包含相邻区域，优先减少实际折返。

### 6.3 顺序与真实交通复核

- 在固定预约之间分别做低成本插入和局部交换；限制最多 3 个完整分组/顺序方案。
- 先用内存距离和保守估时粗筛，再只查询入围路线的相邻段；不要为全部候选构建真实 N×N 路线矩阵。
- 调用当前排程器和独立校验器，发现超时时局部交换、移日或请求缺口候选；每次仍受共享路线数和总时限限制。
- 同模式、同坐标端点、适用时间条件一致的路线可复用；方向不同、模式不同或端点改变不得误命中。支持出发时间的接口还须纳入时间键，不支持时明确估算限制。
- 校验通过后才比较软目标；优先减少交通和不必要变动。用户指定地点不因追求短路径而丢弃。
- “少走路”同时参考路线步行字段与景区内部资料；内部数据未知时显示未核实，不能用直线距离直接宣布满足步行上限。

### 6.4 接入现有规划与调整

新增 `CandidateSelectionPlan`，包含允许普通候选、保护集合、每日期望分组、备选和解释。`llm.py` 只能在该范围选择并提出分组建议；LLM 不编造 POI 或改变字段证据。

调整 `planner.py` 的全目录补齐行为：不得绕过准入把被排除或低质量截断的普通地点重新加入。需要补充时从明确备选池取，并记录原因；资料不足进入有界补查或返回部分方案。

`replanning.py` 复用同一排序与空间工具，但只能作用于允许修改的日期和普通候选；保留 `reselect` 权限与 `require_reselection` 目标的区别。未允许替换时只能移动和重排，不自动换掉已选地点。

### 验收

- 保护项、指定日期、预约和冻结日期相关回归全部通过；超预算停止，失败方案不能保存。
- 至少提供一组“原先跨区折返，新版本按区域组织”的完整对比，包含候选与真实/夹具交通依据。
- 在相同测试资料和预算下报告交通时长、相关性、冗余和上游请求变化；空间方案不能用更多硬条件违规换取更短路线。
- 新版本不得为每个候选对调用高德；并发、缓存及有限补查测试覆盖实际请求数。

## 7. M4：将候选与冲突变成用户能操作的界面

### 交付

1. **候选卡**：匹配理由、主题、时长范围、已知/估算/未知属性、来源、加入必去、留作备选、不感兴趣。备选不自动占用行程。
2. **地点引用**：自然语言框支持选择已有地点生成引用，提交稳定地点 ID 和显示名称；手打名称继续走消歧。服务端重新验证引用是否属于当前旅行及版本。
3. **冲突选择卡**：从已校验方案生成“移到第二天”“替换一个普通推荐”等选项，显示涉及活动、交通差异和待确认项。
4. **变更对比**：复用现有 proposal/version，展示地点、日期、顺序、开始时间与删除原因；只有无阻断错误的选项可确认。

卡片由服务端输出经过 Schema 校验的有限类型，例如 `place_options`、`hotel_options`、`conflict_options`、`change_preview`。前端采用自己的 React 组件目录，首轮无需引入 A2UI/AG-UI 全套依赖；后续确有协议互通需求再接入。

选择卡绑定 `base_version`、proposal ID 与有效选项 ID。用户点击后仍经服务端重新验证和 CAS 提交；前端按钮、模型文案或缓存不能绕过确认。系统只能说“有限搜索未找到可行方案”，不能把预算内未找到描述成数学上无解。

涉及放宽硬条件的选项必须明确说明要求用户修改哪个条件；用户选择后产生新的需求预览，不自动改原要求。

### 验收

- 桌面与手机均可选候选、引用地点、查看冲突选项、取消、确认和刷新恢复。
- 过期选项、重复点击、伪造地点 ID、取消后重试不会污染已确认行程。
- 未验证的模型建议不得显示为“已可执行”；所有禁用按钮都有可见原因。

## 8. M5：研究复用、按需调度与恢复

### 8.1 依赖与复用

为研究产物记录输入指纹、策略/Schema 版本、资料时间、有效期和依赖 ID。只对语义上相关的字段计算指纹；不能把包含 Key 的整份运行配置序列化进数据库。

| 变化 | 需要重新计算 | 通常可保留 |
| --- | --- | --- |
| 酒店选择 | 对应前后接驳、相邻日期可行性 | 已有攻略、其他日期行程、未变化地点证据 |
| 日期 | 天气覆盖、预约/营业日期适用性、相关日程 | 未过期的 POI 身份和位置 |
| 兴趣或同行偏好 | 查询计划、匹配排序、需要的资料缺口 | 同城可复用的 POI 基础数据 |
| 普通地点顺序 | 受影响路线与时间线 | 有效地点资料和不相关研究 |
| 城市、Provider 或坐标 | 对应目录、依赖路线与研究 | 已保存历史版本作为只读记录 |

复用必须匹配城市、输入、来源时效和适用条件。读取旧版本仍使用旧快照；刷新资料产生新的预览，不直接覆盖历史。

### 8.2 按需编排

在现有 LangGraph 上增加结构化 `TaskPlan`：任务角色、依赖、交付 Schema、允许工具、预算和验收项。规则能明确识别的酒店查询、单点问答、局部调整直接路由；复杂需求可让主 Agent 提议任务，再由程序检查。

- 攻略、天气等独立资料可并行研究；同 Key 的高德 HTTP 仍由共享网关串行调度。
- 酒店候选依赖路线末站和次日首站，继续在路线草案之后研究。
- 子 Agent 接收必要需求和引用，交付带来源 ID 的结构化结果；原始网页仍留在各自任务上下文。
- 固定检查不改成额外的 LLM Agent。主 Agent 负责语义判断与取舍，程序负责身份、预算、排程及提交。

### 8.3 持久化执行

先实现单机单 worker 的恢复，再评估多进程或 Redis。运行请求必须落库；worker 用租约、心跳、尝试次数和条件更新领取任务，重复启动不能同时执行同一阶段。

阶段产物按 `run_id + stage + input_hash` 去重，恢复前检查需求版本和资料有效性。完成研究后崩溃可复用产物；外部请求成功但结果尚未落库的窗口可能产生重复查询，记录为至少一次执行，不承诺恰好一次计费。

如引入 LangGraph checkpointer，需要明确其负责执行恢复，已有 proposal/version 负责用户确认状态。持久化节点输入不得包含 Key；在 worker 执行时从本地配置重新解析凭据。需要人工选择时持久化等待状态，释放 worker，不维持阻塞线程。

凭据不可用时进入可见的等待配置/失败状态，不在队列或 checkpoint 中备份明文 Key；凭据在等待期间更换时重新检查 Provider 能力。

### 验收

- 在研究完成后中断服务，重启能继续有效阶段，已确认行程不变。
- 双重领取、重复投递、过期 base_version、超时、取消和恢复都有回归验证。
- 修改酒店不重新搜索全部攻略；修改旅行日期不会错误复用旧天气。
- 新表和 checkpoint 经迁移管理，实际 PostgreSQL 集成测试完成前不宣称已支持生产多 worker。

## 9. M6：真实出行时的使用入口

按收益选择实施：今日行程、下一站导航、已完成/跳过、延误后调整剩余活动，以及打印/导出。

实际执行状态单独保存，绑定行程版本和稳定活动身份。已完成活动不参与未来重规划；恢复旧计划时也不能把已完成记录直接抹掉。地图与导出复用同一已确认快照，不另发模型生成另一份行程。

首轮打印页面即可覆盖离线查阅需求；路线没有真实导航几何时保留示意标记，不用直线冒充导航路径。

## 10. 建议代码拆分与每次交付边界

按职责增加小模块，名称可在实施时调整：

| 模块 | 职责 |
| --- | --- |
| `travel_profile.py` | 需求归一化、语义解析与澄清 |
| `place_evidence.py` | 属性证据、旧数据适配、未知与适用范围 |
| `candidate_discovery.py` | 查询计划、缺口补查、合并与身份检查 |
| `candidate_ranking.py` | 准入、相关性、多样性、选择说明 |
| `spatial_planning.py` | 距离粗筛、日期分组、有限顺序候选 |
| `task_routing.py`（M5） | 按需任务计划与依赖失效 |
| `runtime.py`（M5） | 持久化领取、租约、恢复与取消 |

Provider HTTP 仍集中在工具/网关层；版本事务继续由 `services.py` 管理。前端从 `App.tsx` 抽出画像表单、候选卡和冲突卡，避免继续把全部功能堆进主组件。

实施提交建议依次拆成：M0 数据与评测 → M1 契约/迁移 → M2 检索 API/前端 → M3 排序 → M3 空间规划 → M4 卡片 → M5 执行。每次只开启已完成验收的路径，保留旧生成策略用于离线对比，不允许线上异常静默退回旧目录或演示数据。

每一步完成后交付：变更说明、可演示输入、测试结果、质量变化、仍未核实的信息。只新增与行为风险相关的契约、约束、版本和浏览器测试，不为展示数量编写重复测试。

## 12. 阶段结束应能展示的证据

1. 同一城市的两类用户画像产生不同查询与候选，可追溯到用户表达。
2. 每个候选有真实身份和坐标，旅行属性可区分证据、估算与未知。
3. 同资料下，新路线减少不必要折返和同类活动堆积；给出逐任务对比，不挑选单个最好案例代替整体结果。
4. 用户移动指定地点后，系统保留日期要求、预约和住宿，预览实际变化；失败时给出可操作选项。
5. M5 完成后可演示研究中断恢复，并说明为什么没有重复覆盖确认版本。
6. 面试表述使用实测指标：检索质量、约束通过、变化范围、调用与延迟。测试通过数单独列出，不充当推荐质量指标。

推荐首先执行 M0：整理代表任务与原方案输出；随后 M1～M3 改候选主链路。没有基线时难以判断“更复杂的 Agent”是否真正改善旅行规划。
