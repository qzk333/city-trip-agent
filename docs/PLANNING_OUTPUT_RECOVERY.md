# 晚间调整未生效：输出校验与恢复

> 历史实施记录：其中晚间优先、固定阈值和地点唯一等策略已调整，当前行为以[约束政策](CONSTRAINT_POLICY.md)为准。

日期：2026-10-27。

## 原因与证据

最近一次深圳运行 `b392facc743c42cc99291e6997be434b` 的首次时间表存在晚间留白。独立审核报告确实送到了主 Agent，第二次模型生成也确实执行了，但结果没有进入排程阶段：返回输出未通过解析校验，保留第一版。

历史日志只保存笼统的 `invalid_schedule`，没有原始失败响应，不能逐字段还原或断言所有历史失败同因。本轮使用相同需求、候选、天气、攻略 brief、审核反馈和上一版计划隔离复现，捕获到具体问题：华强北博物馆在两天内出现三次，深圳中心公园跨天出现两次。代码拒绝这种结果合理；这不是合法晚间活动被营业或交通校验删掉。

程序同时存在恢复缺陷：`place_ids` 缺省时，先从时间表派生候选索引，随后在索引唯一性/长度检查处直接抛错。JSON 解码、根节点、候选索引等检查也位于原先的时间表格式纠正分支之外。因此，这类错误没有把具体重复位置返回模型，主 Agent 就结束了修改。

另一个问题是选版只统计问题条数。新版本即使少遗漏一晚，也可能因为新增其他问题、总问题数相同或更多而被旧版本压过。界面又没有明确区分修改请求已执行和修改结果已采纳。

## 针对性修复

1. `planning_output.py` 对完整规划做统一解析，先验证时间表，报告具体日期、活动位置与重复 POI，再检查冗余索引。没有自行删点、改分天或接受目录外 ID。
2. JSON、日期、时间 schema、未知/重复地点和索引冲突进入同一纠正流程。具体错误及全程地点使用清单交回主模型，保留原审核意见，说明已用/未用候选，要求全程唯一分配。
3. 每次 `model_candidates` 仍最多四个模型请求，最多六次本地目录工具执行；在已有请求预算内最多两次输出纠正。相同错误明细再次出现即停止，不盲目重试；仅错误发生变化且还有预算时继续。输出纠正不增加地图查询。
4. 所有核心字段通过后才写入 recommendations。失败保存结构化 `code/field/message`，不持久化凭据、供应商错误正文或校验失败值。
5. 选版先比较硬冲突，再考虑审核是否完成、审核指出的晚间缺失天数与其他问题；同等可行且已审核的修改版可被采纳。硬约束不被体验分数覆盖。
6. `review_outcome` 与 `selected_attempt` 随预览和版本保存。页面区分已采纳、保留原版、修改失败和预算不足，失败原因可展开。是否改变时间表比较的是程序核算后的地点、实际时段、用餐/休息，不因仅重写理由就称为调整成功。

时间重叠、交通可达、已知营业时间、预约、锁定、必去和指定日期等校验保持有效。本轮不新增无限自主搜索，不替用户勾选酒店，也不强行用程序往每晚塞点。

## 验证与实际边界

新增回归覆盖统一错误纠正、跨日重复的全部位置、第二天字段定位与脱敏、相同错误停止重试、错误变化使用最后一个现有请求预算、主模型—审核—重复纠正—晚间活动闭环、错误版本不落地、选版优先减少晚间遗漏，以及仅修改理由不能宣称时间表已调整。

对本轮捕获的错误响应进行回放，再调用真实模型纠正：原流程在第二个响应直接失败，新流程在总计四个请求内取得不重复的两日时间表，其中两个请求为已捕获响应回放、两个为真实纠正。未写入用户数据库。

再用已有交通快照和五次新高德路线查询独立复核，该时间表没有硬冲突，第一晚出现 19:30—20:40 的中心公园活动。第二天仍在 17:50 结束，独立审核继续返回 `changes_requested`。因此，本轮证明了早退恢复、部分有效修改能被采用和剩余问题可追踪，不能声称模型已经完全解决两晚规划，也不能证明夜间场所实际开放。相关只读验证产物位于被 Git 忽略的 `artifacts/`。

无需数据库迁移；旧确认行程及本地 API 配置不被改写。

最终验证：307 项后端测试、68 条桌面/手机浏览器回归、Ruff 检查与格式、前端格式与生产构建通过。
