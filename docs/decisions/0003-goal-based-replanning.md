# 目标驱动的有限重规划

日期：2026-10-23。

原实现把自然语言直接变为编辑操作，再按固定的日期分组排程。移动景点导致目标日过满时，只返回 `revision_incomplete`，不能协调其他普通活动。

采用“目标解析 → 最小修改 → 冲突反馈 → 有限重规划 → 独立校验 → 用户确认”。酒店、抵离、预约、锁定、必去及明确指定的地点日期为硬约束；原普通活动的分组和顺序为偏好。未允许重选时保留原地点集合；允许重选时可替换普通推荐，并提供实际新增、移除和移动说明。

默认可协调来源/目标日期；单日新增或时间变化可扩大至相邻日期，跨日操作包含中间日期。用户可选择只执行指定修改或全程协调，也可在自然语言中冻结日期。模型只能输出目录 ID 的日期分配，程序计算路线、时长和检查。

最多 3 轮模型协调、2 次景点查询、每次 5 条，共用运行时间和路线预算。失败查询也消耗预算。原始攻略页与酒店研究上下文不进入重规划，额外目录限制为最近 24 个普通候选。

对于普通跨日协调，程序最多尝试 4 个单地点转移并验证，供模型参考。模型输出不合规时可提供明确标注的程序可行方案，不能把无效结果说成成功。首次生成不变，不宣称全局最优或覆盖所有可行路径。

增量景点沿用高德关键字/周边查询和共享网关，过滤非目标类型、异地和错误坐标。模型不得编造坐标或证据。未知具名地点未唯一确认时停止，泛类新增须实际选入新的候选。接口依据：[高德搜索 POI 文档](https://lbs.amap.com/api/webservice/guide/api-advanced/search)。

`place_days` 随需求保存。`0005` 为 proposal/version 增加目录快照，需求、目录、行程一起原子确认，取消和恢复历史处理相同快照。旧需求的指定日期仅从已确认且仍适用的任务恢复，不跨越历史恢复边界推断。

每轮决策、错误、查询证据、路线数以及服务商提供的 Token/延迟留在任务结果中。数据真实性、营业预约核实、模型理由的证据蕴含、跨进程恢复与分布式限流仍是后续工作。
